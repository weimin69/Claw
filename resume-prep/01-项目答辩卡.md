# agent-cli-rust 项目答辩卡

> 用途：面试前 10 分钟快速过一遍。每个问题都要能用自己的话讲 1–2 分钟。
>
> 原则：只讲能解释的内容；不确定的边界主动说“目前没做”。

---

## 0. 30 秒介绍

这是一个用 Rust 写的终端 SWE Agent。用户给出一个自然语言任务，它在授权的工作区内探索仓库、读写文件、执行命令、运行测试，并根据结果继续下一轮，最后汇总改动和命令。核心不是聊天，而是“模型决策 + 工具执行 + 可验证的编码闭环”。

如果面试官只给 30 秒，就说这一句，然后停住，等对方追问。

## 1. 一张架构图

```text
main.rs / cli.rs
   │  解析命令、参数、退出码
   ▼
commands/claw.rs
   │  组装配置、Workspace、模型、工具执行器、会话
   │  交互循环、事件展示、结果汇总
   ▼
AgentSession + AgentState              agent.rs
   │  完整历史、工作上下文、上下文预算
   │  每轮迭代/工具次数预算
   ▼
run_turn / run_turn_loop
   │
   ├── AgentModel ──────────────── openai_compatible.rs
   │      ChatEndpoint：HTTP、超时、重试、响应解析
   │      OpenAI-compatible API
   │
   └── ToolExecutor ────────────── tools.rs
          BuiltinToolExecutor
          ├── Workspace：路径边界
          ├── read/list/search：只读
          ├── replace_text / create_file：需 --allow-write
          └── run_command：需 --allow-exec

AgentEvent / ToolEffect
   │  运行事件、真实发生的文件/命令效果
   ▼
CLI 统计与变更报告 + session.rs 会话存档
```

一句话概括：

> CLI 负责组装和展示，`AgentSession` 负责历史和上下文，`run_turn_loop` 负责“模型—工具”循环，`AgentModel` 和 `ToolExecutor` 是两个可替换边界。

## 2. 一次请求的完整链路

以 `claw` 单次任务为例：

1. `cli.rs` 解析参数；`commands/claw.rs` 读取 TOML 配置，检查 API key，创建 `Workspace`。
2. 根据 `--allow-write` / `--allow-exec` 创建 `BuiltinToolExecutor`；模型适配器也按同样授权声明工具。
3. `AgentSession::run_turn` 取出现有工作上下文，追加新的用户消息。
4. 请求前做上下文预算检查；必要时从最旧的完整轮次开始裁剪。
5. 进入 `run_turn_loop`：先检查迭代预算，再调用 `AgentModel::next_decision`。
6. 模型返回两种结果之一：
   - `FinalAnswer`：记录 assistant 消息，结束本轮；
   - `ToolCalls`：记录整批工具调用，逐个执行。
7. 每个工具调用先经过执行器权限检查，再由 `Workspace` 解析路径，最后执行。
8. 工具结果包装成 `AgentMessage::ToolResult`，连同 `is_error` 回填给模型，进入下一轮。
9. 最终返回 `AgentRunResult`：回答、迭代数、工具次数、`ToolEffect` 列表。
10. CLI 打印变更文件、执行命令、工具统计；成功轮次写入会话存档。

关键点：**工具错误可以回到模型，致命错误才结束运行。** 这是整个 Runtime 最重要的错误边界。

## 4. 三个核心问题卡

### 卡片 1：模型 429/503 导致整个会话中断

**现象**

联调时一次限流或网关错误就会让 `claw` 退出；交互模式下当轮上下文丢失，用户只能重开。

**根因**

- 请求路径没有区分“可重试的传输错误”和“不可重试的客户端错误”。
- 重试如果放进 Agent Runtime，会污染模型/工具循环，也会让 Runtime 感知 HTTP 状态码。

**方案**

- 抽出 `ChatEndpoint`，统一 `agent` 和 `chat` 的请求、超时和重试。
- `RetryPolicy` 默认 3 次尝试，确定性退避 1s、2s，单次上限 30s。
- 只重试：408、429、500、502、503、504，以及连接失败、超时、请求中断、响应体读取失败。
- 不重试：400/401/403/404 等客户端错误、请求构建失败、2xx 但 JSON 非法。
- `Retry-After` 只解析整数秒，并截断到 30s。
- 通过 `RetryNotice` observer 把提示交给 CLI，传输层不直接打印。
- 用 Wiremock 覆盖：503→200、连续 503 耗尽、400 不重试、超时后重试成功。

**取舍**

- 退避是确定性的，便于测试复现，但没有随机抖动。
- 超时重试可能造成重复计费。
- 重试次数、超时仍是常量，后续应配置化。

**一句话总结**

> 把重试放在传输层，只重试无副作用的模型请求；Runtime 不感知 HTTP 状态码。

---

### 卡片 2：工具失败要不要终止 Agent

**现象**

文件不存在、参数非法、命令非零退出，如果都当成致命错误，Agent 就没有机会根据错误自我修复。

**根因**

可恢复的工具失败和致命的执行器失败混在同一个错误通道里。

**方案**

- `ToolOutput` 表示工具结果，带 `is_error` 和 `effects`。
- `ToolOutput::error` 是可恢复失败：文件不存在、参数非法、未知工具、命令非零退出、超时。
- `ToolExecutor::execute` 外层返回 `Err` 才是致命失败：执行器内部错误、无法继续的运行时问题。
- 可恢复错误被序列化成 JSON tool message，按工具调用 ID 回填给模型。
- 单轮多个工具调用作为一条 `AssistantToolCalls` 消息保存；结果按顺序回填。
- 工具预算按整批检查：一批会超限就整批不执行，避免部分执行造成状态不一致。

**取舍**

- 模型可能反复尝试同样的失败操作，需要迭代/工具次数预算兜底。
- 致命/可恢复的边界是设计判断，不是类型系统自动保证的。

**一句话总结**

> 工具失败是模型可观察的事实，不是 Runtime 的终点；只有执行器本身不可继续时才终止。

---

### 卡片 3：命令超时、输出洪水、Ctrl+C 后子进程残留

**现象**

- 命令挂起会拖死整个任务。
- 子进程输出太多会写满管道，父进程等待 EOF 时可能死锁。
- Ctrl+C 后只杀直接子进程，后代可能残留。

**方案**

- `run_command` 接收程序名 + 参数数组，不经过 shell，避免字符串拼接和隐式解析。
- 工作目录必须在 workspace 内；默认超时 60s，允许 1–300s。
- stdin 关闭；stdout/stderr 并发排空，避免管道背压死锁。
- 每个流只保留前 32 KiB，超出后继续排空但不保留。
- 非零退出、超时都作为可恢复工具错误返回模型，并带上退出码、耗时、截断标记。
- Unix 下使用独立进程组 + RAII guard，超时或 Future 被丢弃时终止进程组；直接子进程启用 `kill_on_drop`。
- 子进程启动前移除 `AGENT_CLI_LLM_API_KEY` 和 `OPENAI_API_KEY`。

**取舍**

- 32 KiB 截断会丢失后续输出，但保证内存和上下文有界。
- 进程组只能清理留在组内的后代；脱离进程组的后代仍可能逃逸。
- 这不是 OS 沙箱；`--allow-exec` 仍然是范围很广的授权。

**一句话总结**

> 命令执行的核心不是“能跑”，而是超时、输出背压、进程清理和权限边界都可控。

## 5. 备选问题（面试官追问时用）

| 问题 | 关键回答 |
|---|---|
| `../` 或外部符号链接怎么防？ | `Workspace::new` 先 canonicalize 根目录；`resolve_existing` 对目标 canonicalize 后检查 `starts_with(root)`；`resolve_new_file` 只解析已存在的父目录，再检查目标不存在的状态。边界检查不是沙箱。 |
| 多次替换怎么避免写坏文件？ | `prepare_edit` 在内存中按顺序应用 1–100 个 edit，校验唯一匹配、重叠、越界和大小；全部成功才由 `apply_edit` 一次保存。保存前复查路径、类型、权限和内容，同目录临时文件写入并同步后替换。 |
| 长对话超上下文怎么办？ | 默认 256 KiB 的“内部消息 JSON 字节”预算，不是 token；请求前从最旧完整轮次开始裁剪，完整历史仍保留在磁盘。输入自身超限则不发送。 |
| 会话存档怎么保证不写坏？ | 同目录临时文件 + `sync_all` + 原子发布；加载时校验版本、workspace、消息顺序、工具 ID/名称配对；Unix 新文件 0600。失败保留上次成功快照。 |
| 为什么不做并发工具调用？ | 当前按模型返回顺序串行执行，保持消息顺序和错误语义简单；读工具以后可以并行，但写工具和命令需要更复杂的事务/冲突处理。 |

## 6. 关键数字与边界

| 项目 | 值 | 说明 |
|---|---|---|
| 模型重试 | 3 次尝试，1s/2s 退避，30s 上限 | 仅无副作用的模型请求 |
| 命令超时 | 默认 60s，范围 1–300s | 超时返回可恢复错误 |
| 命令输出 | stdout/stderr 各 32 KiB | 继续排空，避免死锁 |
| 文件大小 | 1 MiB | 读写和编辑都有限制 |
| 列表 | 200 项 | `list_files` 截断 |
| 读取 | 500 行 / 32 KiB 正文 | `read_file` 截断 |
| 上下文 | 256 KiB 内部 JSON | 不是 token |
| 会话存档 | 16 MiB | v1–v3 |
| 测试 | 217 个 | 不依赖真实 API |

这些数字的作用不是炫耀，而是证明你考虑过**有界执行**。面试官问“如果文件特别大/命令输出特别多/对话特别长怎么办”，你可以直接指到这些边界。

## 7. 十个必背追问

### Q1. 为什么用 Trait 抽象模型和工具？

> 把 Runtime 和具体 Provider/工具实现解耦，测试时可以用 fake model / fake executor 驱动确定性流程。只保留 `AgentModel` 和 `ToolExecutor` 两个必要的边界，没有做过度抽象。

### Q2. 为什么工具调用是串行而不是并发？

> 当前优先保证消息顺序、错误语义和状态一致性。多个工具调用按模型返回顺序执行，结果按同一顺序回填。读工具以后可以并行，但写工具和命令会引入冲突和事务问题，暂不引入。

### Q3. 怎么防止 Agent 无限循环？

> 三道限制：最大迭代次数、最大工具调用次数、上下文预算。工具预算按整批检查，超限整批不执行。默认可以不设预算，但无人值守场景应显式配置；目前还没有“无进展检测”。

### Q4. 工具失败为什么不让整个 Agent 退出？

> 文件不存在、命令非零退出这类失败是模型可以观察并修正的事实。可恢复错误通过 `ToolOutput::error` 回填给模型；只有执行器内部不可继续的错误才用外层 `Err` 终止。

### Q5. workspace 越界和符号链接怎么防？

> 启动时 canonicalize 根目录；所有路径通过 `Workspace` 解析，canonicalize 后必须仍在根目录下；新建文件只解析已存在的父目录，并拒绝已存在的目标。它防的是路径越界，不是并发替换或 OS 级沙箱。

### Q6. 重试会不会重复执行工具或重复计费？

> 只重试模型请求，不重试工具执行；工具失败仍然作为工具结果回给模型。超时重试确实可能重复计费，这是当前已知限制，没有做 idempotency key。

### Q7. 命令超时后子进程怎么清理？

> Unix 下命令在独立进程组里运行，超时或 Future 被取消时通过 RAII guard 终止整个进程组；直接子进程还有 `kill_on_drop`。脱离进程组的后代仍可能逃逸，README 里明确写了这个限制。

### Q8. 会话存档如何保证不写坏？

> 同目录临时文件写完、`sync_all` 后再原子替换；保存前确认目标没有被外部改过；加载时校验版本、workspace、消息顺序和工具调用配对。失败不会覆盖上次成功快照。

### Q9. 为什么上下文预算按字节而不是 token？

> 字节数可以直接从内部消息 JSON 精确计算，不依赖 tokenizer，测试确定性强。缺点是它不等于模型真实窗口；目前没有 token 估算和自动摘要，这是技术债。

### Q10. 这个项目最大的限制是什么？如果重做会改哪里？

> 没有 OS 沙箱和逐命令审批，`--allow-exec` 权限很宽；失败轮次仍会关闭会话；没有流式输出、token 预算和结构化 trace。优先会补逐命令审批和会话失败回滚，再做 token 预算/摘要。

## 8. 被问“AI 参与了多少”怎么答

不要含糊，也不要过度道歉。可以用这个结构：

> 这个项目是我从学习项目逐步迭代成 SWE Agent 的。AI 在部分模块的代码实现上参与较多；我负责需求拆解、架构边界、接口约束、失败路径设计、测试验收和问题定位。比如重试分类、`ToolOutput` 的错误分层、命令进程组清理，这些决策和验收我可以展开讲。

然后立刻接一个具体问题卡，把话题拉回技术细节。

如果面试官追问“哪部分不是你写的”，如实说具体模块，并补一句：

> 这部分代码由 AI 辅助生成，但我读过实现、能解释调用链，也补过测试/修过问题。您可以挑一个失败路径问我。

**不要做**：把 AI 生成说成全部手写；被追问时临时编造；用“我主要做架构”掩盖讲不清实现。

## 10. 红线：这些不要写/不要说

- 不要说“实现了完整沙箱”——目前只有路径边界检查，没有 OS 隔离。
- 不要说“支持所有模型”——目前是 OpenAI-compatible API。
- 不要说“token 预算/自动摘要”——目前是字节预算，没有摘要。
- 不要说“完整 patch / 多文件事务”——目前是单文件精确替换 + 不覆盖创建。
- 不要说“多智能体/插件系统/MCP”——未实现。
- 不要说“零 bug/生产级”——这是 pre-release，README 明确列了限制。
- 不要把团队项目或 AI 生成的代码说成完全独立手写。
