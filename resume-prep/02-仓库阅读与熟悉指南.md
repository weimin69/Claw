# 如何阅读自己的仓库并真正熟悉

> 目标不是“看完 1 万行”，而是建立能讲、能画、能改、能定位问题的心理模型。
>
> 建议用三个晚上完成；如果时间紧，至少完成第 1 晚和第 2 晚的失败实验。

---

## 1. 先定三层目标

| 层级 | 标准 | 用途 |
|---|---|---|
| L1 全局 | 1 分钟讲清项目做什么；5 分钟画出架构图 | 简历筛选、自我介绍 |
| L2 深水区 | 能讲 3 个问题的现象/根因/方案/取舍/验证；能追踪一次请求 | 技术面试主战场 |
| L3 动手 | 能独立加一个小功能或补一个失败测试；能定位一个 bug | 证明“我真的做过” |

不要试图把每个模块都做到 L3。**L1 全覆盖 + 3 个 L2 + 1 个 L3** 就足够防守。

---

## 2. 准备：先保证基线是干净的

在开始阅读前，确认当前仓库状态，避免把阅读过程中的实验和真实修改混在一起。

```bash
git status
cargo test
cargo clippy --all-targets -- -D warnings
cargo fmt --check
```

如果要做“故意改坏再修”的实验，先开一个练习分支：

```bash
git switch -c practice/repo-reading
```

阅读期间不要动 `Config.toml`，不要 `cat` 它，避免把 API key 打到终端或日志里。

准备一个笔记文件，每个模块记六项：

```md
## 模块名

- 职责：
- 输入 / 输出：
- 失败路径：
- 关键取舍：
- 对应测试：
- 我还没弄懂的问题：
```

---

## 3. 阅读顺序：先骨架，后边界，最后历史

### Pass 1：读文档，建立地图（30–45 分钟）

按这个顺序读：

1. `README`
   - `STATUS`：项目现在能做什么
   - `TOOLS`：工具能力与限额
   - `PERMISSIONS AND SAFETY`：安全边界
   - `SESSIONS` / `CONTEXT BUDGET`：会话与上下文
   - `EXECUTION REPORT`：每轮结束输出什么
   - `LIMITATIONS`：哪些没做
2. `PROJECT_STATUS.md`
   - `Current Milestone`
   - `Completed`
   - `Architecture Notes`
   - `Technical Debt`
3. `LEARNING_ROADMAP.md`
   - 只看 Phase 0–8 的目标和验收标准，不用逐条背
4. 选读 journal：
   - `journal/2026-11-02.md`：重试
   - `journal/2026-10-19.md`：命令执行、会话
   - `journal/2026-10-18.md`：文件编辑
   - `journal/2026-10-16.md`：ToolOutput、多工具调用
   - `journal/2026-10-21.md` / `2026-10-22.md`：事件、存档、恢复

读完后，用一句话回答：

> 这个项目的主链路是什么？哪些是核心，哪些是外围？

参考答案：

> 核心是 `claw` 里的“模型—工具—模型”循环；配置、展示、会话、命令执行都是围绕这个循环的服务。

### Pass 2：读骨架，画出调用图（45–60 分钟）

只读这四个文件，先不要陷入细节：

1. `src/main.rs`
2. `src/cli.rs`
3. `src/commands/claw.rs`
4. `src/agent.rs`

重点看函数边界，不要逐行读实现：

- `main.rs`：入口、`run()`、错误输出、退出码
- `cli.rs`：`Cli`、`Commands`、`Claw` 参数
- `commands/claw.rs`：`execute` 如何组装依赖；`run_interactive` 如何循环
- `agent.rs`：`AgentMessage`、`ToolOutput`、`AgentState`、`AgentSession`、`run_turn`、`run_turn_loop`

画一张图，只画箭头和职责，不抄代码。画完对照 `01-项目答辩卡.md` 的架构图。

### Pass 3：读边界，理解“为什么这么设计”（60–90 分钟）

按“边界”而不是按文件读：

| 边界 | 看什么 | 要回答的问题 |
|---|---|---|
| 模型边界 | `AgentModel`、`OpenAiCompatibleAgentModel`、`ChatEndpoint` | 为什么 Runtime 不感知 HTTP 状态码？重试为什么在传输层？ |
| 工具边界 | `ToolExecutor`、`BuiltinToolExecutor` | 权限在哪里检查？可恢复错误和致命错误怎么分？ |
| 工作区边界 | `Workspace` | 路径越界、符号链接、新建文件分别怎么处理？ |
| 会话边界 | `AgentSession`、`SessionStore` | 完整历史和工作上下文的区别？存档如何校验和原子保存？ |
| 上下文边界 | `context_start`、`check_context_size` | 为什么按完整轮次裁剪？为什么按字节？ |
| 命令边界 | `tools/command.rs` | 超时、输出背压、进程组清理分别怎么实现？ |
| 编辑边界 | `tools/edit.rs` | 为什么先 prepare 再 apply？如何避免部分写入？ |

每个边界至少找到一个失败测试，读测试名和断言。

### Pass 4：读测试，把测试当规格（45 分钟）

测试不是附属品，是这个项目最诚实的文档。优先读：

- `src/agent.rs` 的 `#[cfg(test)]`：预算、上下文、事件、错误分层
- `src/openai_compatible.rs`：重试分类、超时、请求/响应映射
- `src/workspace.rs`：越界、符号链接
- `src/session.rs`：版本、顺序、原子保存、恢复
- `tests/coding_workflow.rs`：端到端“探索—修改—执行—修复”
- `tests/claw_cli.rs`：CLI 行为、权限、交互
- `tests/session_resume.rs`：跨进程恢复
- `tests/context_budget.rs`：上下文裁剪

读测试时问自己：

> 这个测试在保护什么行为？如果删掉实现，哪个断言会先失败？

### Pass 5：读历史，理解演进（30 分钟）

```bash
git log --oneline --decorate --graph -20
git log --stat -5
git log --oneline -- src/agent.rs
git log -S "RetryPolicy" --oneline
git show <commit> --stat
git show <commit> -- src/openai_compatible.rs
```

不要看所有 commit。挑 3 个关键节点：

- `feat: add agent tool calling protocol support`
- `feat: add workspace-aware repository tools and runtime controls`
- `feat: retry transient model failures and drop leftover add tool`

看每个 commit 解决了什么问题、改了哪些模块、测试怎么变。这样你能讲“项目是怎么长出来的”，而不是“代码现在长这样”。

### Pass 6：合上电脑，讲一遍（30 分钟）

不看笔记，做三件事：

1. 在白纸上画架构图。
2. 用 2 分钟讲一次请求链路。
3. 挑一个失败路径，讲现象、根因、方案、取舍、验证。

讲不顺的地方，就是下一次要补的地方。

## 4. 代码入口地图

行号会变，优先用函数名搜索。

| 入口 | 位置 | 看什么 |
|---|---|---|
| 程序入口 | `src/main.rs` `main` / `run` | Tokio 入口、错误输出、退出码 |
| 命令定义 | `src/cli.rs` `Cli` / `Commands` | `claw` 的参数和默认值 |
| 组装与交互 | `src/commands/claw.rs` `execute` / `run_interactive` | 配置、Workspace、模型、执行器、会话如何接起来 |
| 单轮执行 | `src/agent.rs` `AgentSession::run_turn` | 工作上下文、预算、失败关闭 |
| 核心循环 | `src/agent.rs` `run_turn_loop` | 模型决策、工具调用、结果回填、终止 |
| 上下文裁剪 | `src/agent.rs` `context_start` / `check_context_size` | 完整轮次、字节预算 |
| 模型适配 | `src/openai_compatible.rs` `next_decision` / `build_agent_chat_request` | 消息映射、工具 schema、响应解析 |
| HTTP 与重试 | `src/openai_compatible.rs` `ChatEndpoint::complete` / `send_once` | 重试分类、退避、`Retry-After` |
| 工具分发 | `src/tools.rs` `BuiltinToolExecutor::execute` | 权限检查、`spawn_blocking`、错误包装 |
| 路径边界 | `src/workspace.rs` `resolve_existing` / `resolve_new_file` | canonicalize、越界、符号链接 |
| 文件编辑 | `src/tools/edit.rs` `prepare_edit` / `apply_edit` | 批量编辑、唯一匹配、原子保存 |
| 命令执行 | `src/tools/command.rs` `execute` | 进程组、超时、输出限额 |
| 会话存档 | `src/session.rs` `SessionStore::save` / `resume` | 原子写入、校验、恢复 |
| 端到端测试 | `tests/coding_workflow.rs` | 脚本化模型 + 真实工具 |

## 5. 追踪一次请求：按这个顺序打断点/读代码

以 `claw` 单次模式为例：

1. `main.rs::run` 解析 `Cli`，分发到 `commands::claw::execute`。
2. `claw.rs::execute`：
   - 读配置，检查 API key；
   - `Workspace::new` canonicalize 根目录；
   - 根据 `--allow-write` / `--allow-exec` 创建 `BuiltinToolExecutor`；
   - 创建 `OpenAiCompatibleAgentModel`；
   - 如果不是交互模式，`run_agent(...)`。
3. `agent.rs::run_agent` 创建 `AgentSession`，调用 `run_turn`。
4. `run_turn`：
   - 取出 `working_context`；
   - 追加新用户消息；
   - `context_start` 做预算裁剪；
   - 关闭会话（失败保护）；
   - 进入 `run_turn_loop`。
5. `run_turn_loop`：
   - `begin_iteration` 检查迭代预算；
   - `check_context_size` 检查上下文；
   - `next_decision` 发请求；
   - `FinalAnswer` 或 `ToolCalls`。
6. `ToolCalls` 分支：
   - `begin_tool_batch` 检查工具预算；
   - 记录 `AssistantToolCalls`；
   - 逐个 `tool_executor.execute`；
   - 权限检查 → `Workspace` 解析 → 具体工具；
   - 记录 `ToolResult`，`effects` 累积。
7. 回到循环，直到最终回答或预算/错误。
8. 成功后 `working_context` 恢复、`closed = false`；CLI 打印结果；`SessionStore::save` 写快照。

**检查点**：如果你能在每个箭头处说出“输入是什么、输出是什么、失败会怎样”，就算真正理解了主链路。

## 6. 失败实验：比读成功路径更有用

每个实验都先读测试，再运行，再尝试预测结果。

### 实验 1：模型重试分类

```bash
cargo test next_decision_retries_transient_failure_and_reports_notice -- --nocapture
cargo test next_decision_exhausts_retryable_failures -- --nocapture
cargo test next_decision_does_not_retry_client_errors -- --nocapture
```

观察：

- 503 会重试，400 不会；
- 重试提示通过 observer 回到 CLI；
- 耗尽后错误里带尝试次数。

### 实验 2：路径越界

```bash
cargo test rejects_parent_absolute_and_similar_prefix_escape -- --nocapture
cargo test checks_symlink_targets_against_workspace_boundary -- --nocapture
```

观察：`../`、绝对路径、相似前缀（如 `/tmp/ws-evil`）、外部符号链接分别在哪一层被拒绝。

### 实验 3：命令超时与进程组

```bash
cargo test timeout_kills_group_even_if_parent_exited_with_pipes_open -- --nocapture
cargo test cancelling_future_kills_child_group -- --nocapture
```

观察：超时/取消时，为什么只杀父进程不够；RAII guard 在什么时候触发。

### 实验 4：输出洪水

```bash
cargo test returns_nonzero_exit_and_drains_both_pipes_past_limits -- --nocapture
```

观察：为什么超限后还要继续读；如果直接停止读取会发生什么。

### 实验 5：编辑原子性

```bash
cargo test failed_later_edit_never_saves_earlier_changes -- --nocapture
cargo test batch_replacements_save_all_changes_and_report_combined_diff -- --nocapture
```

观察：多个 edit 中后一个失败时，前一个为什么不能落盘；临时文件和 `persist` 在哪里。

### 实验 6：会话校验

```bash
cargo test rejects_incomplete_or_mispaired_history -- --nocapture
cargo test rejects_unsupported_version_and_mismatched_or_invalid_workspace -- --nocapture
```

观察：什么样的历史会被拒绝；工具调用 ID/名称如何配对。

### 实验 7：上下文裁剪

```bash
cargo test context_start_removes_only_as_many_old_turns_as_needed -- --nocapture
cargo test context_start_removes_tool_turn_as_a_whole -- --nocapture
```

观察：为什么不能只删半轮；工具调用和结果为什么必须在一起。

### 实验 8：端到端闭环

```bash
cargo test --test coding_workflow -- --nocapture
cargo test --test context_budget -- --nocapture
```

观察：脚本化模型如何驱动真实文件工具和 `cargo test`；最终如何断言文件内容和退出码。

> 这些测试不依赖真实 API key。不要为了做实验去调用真实模型，Wiremock 足够。

## 7. 如何读一个具体文件：五步法

以 `src/agent.rs` 为例：

1. **看顶部类型和注释**
   - `AgentEvent`：运行事件
   - `ToolEffect`：真实发生的文件/命令效果
   - `AgentMessage`：消息模型
   - `ToolOutput`：工具结果
   - `AgentModel` / `ToolExecutor`：两个边界
2. **看公共函数，跳过 helper**
   - `AgentSession::run_turn`
   - `run_agent`
   - `run_turn_loop`
   - `context_start`
3. **找输入、输出、错误**
   - 输入：`prompt`、预算、model、executor
   - 输出：`AgentRunResult`
   - 错误：预算超限、上下文超限、模型错误、致命工具错误
4. **找调用方和被调用方**
   ```bash
   rg -n "run_turn|run_agent|next_decision|execute\(" src tests
   ```
5. **读测试，写三句话**
   - 这个模块负责什么？
   - 哪条失败路径最重要？
   - 哪个设计取舍最值得讲？

填好的示例：

```md
## agent.rs

- 职责：Agent Runtime 的消息模型、单轮循环、预算、上下文和事件。
- 输入 / 输出：用户 prompt + model + tool executor → AgentRunResult。
- 失败路径：迭代/工具预算超限、上下文超限、模型错误、致命工具错误。
- 关键取舍：可恢复工具错误回填模型；失败/取消后关闭会话，避免复用不完整历史。
- 对应测试：agent::tests 下的 budget/context/events/session 测试。
- 我还没弄懂的问题：为什么失败后不尝试回滚 working_context？（答案在 PROJECT_STATUS 的 Next Step）
```

## 8. 如何读 Git 历史

不要从第一个 commit 看到最后一个。用问题驱动：

- “重试是什么时候加的？” → `git log -S "RetryPolicy" --oneline`
- “这个模块为什么变成这样？” → `git log --oneline -- src/agent.rs`
- “这次提交改了什么？” → `git show <commit> --stat`
- “这行代码谁改的？” → `git blame -L <start>,<end> src/openai_compatible.rs`
- “两个版本差在哪？” → `git diff <old>..<new> -- src/agent.rs`

每看一个 commit，回答三个问题：

1. 之前的行为是什么？
2. 这次解决了什么问题？
3. 有没有留下新的限制/技术债？

这比背当前代码更容易形成“工程叙事”。

## 9. 三个晚上怎么安排

### 第一晚：建立地图（约 2 小时）

- 读 `README` + `PROJECT_STATUS.md` 的架构与限制（30 分钟）
- 读 `main.rs` → `cli.rs` → `claw.rs` → `agent.rs` 的公共接口（45 分钟）
- 画架构图 + 写一次请求链路（30 分钟）
- 用 3 句话解释每个核心模块（15 分钟）

产出：一张架构图、一页模块职责表。

### 第二晚：失败路径（约 2 小时）

- 跑 `cargo test` 基线（10 分钟）
- 做实验 1–4（40 分钟）
- 做实验 5–7（40 分钟）
- 整理 3 张问题卡：现象/根因/方案/取舍/验证（30 分钟）

产出：3 张能讲 5 分钟的问题卡。

### 第三晚：动手与表达（约 2 小时）

- 选一个小功能或一个缺失测试，自己实现（60 分钟）
- 跑测试、clippy、fmt（15 分钟）
- 把项目段改成 4–5 条简历 bullet（20 分钟）
- 对着手机录音讲 3 个问题，回听并删掉含糊的词（25 分钟）

产出：一个真实的 L3 证据 + 一版能投递的简历段。

> 如果只有一晚：读 `README` + `PROJECT_STATUS.md`，跑 `tests/coding_workflow.rs`，整理 3 张问题卡。先保证面试能讲，再补代码细节。

## 11. 可以独立做的小功能

按难度从低到高：

1. **重试次数/超时配置化**：把常量变成 CLI 参数或配置项，补参数校验和测试。
2. **`Retry-After` 支持 HTTP-date**：当前只支持整数秒，补解析和测试。
3. **逐命令审批**：交互模式下允许/拒绝命令，非交互模式显式拒绝；这是 Phase 4.3 的下一步。
4. **会话失败回滚**：失败或取消时回滚 `working_context` 与 `full_history`，保持会话可继续；这是 `PROJECT_STATUS.md` 的 Next Step 第 1 项。
5. **新的只读工具**：例如按 glob 列文件，补 workspace 校验、输出限额和测试。

做的时候遵守三条：

- 开练习分支，不要在主分支上实验。
- 先写测试或至少先写验收标准。
- 做完跑 `cargo test`、`cargo clippy --all-targets -- -D warnings`、`cargo fmt --check`。

不要为了简历去堆功能。**一个自己独立做的小功能 + 能讲清失败路径，比五个 AI 生成的大功能更有价值。**

## 12. 常见误区

| 误区 | 更好的做法 |
|---|---|
| 从 `main.rs` 第一行读到 `session.rs` 最后一行 | 先读公共接口和调用图，再按边界深入 |
| 只看成功路径 | 每个功能至少读一个失败测试 |
| 背代码/背行号 | 记职责、边界、失败路径；行号会变 |
| 把 README 当唯一事实 | 用代码和测试核对，尤其是限制和默认值 |
| 试图讲所有模块 | 选 3 个深水区，其他能一句话带过 |
| 把“用了 AI”藏起来 | 如实说明参与程度，把话题拉回你负责的决策和验收 |
| 为了简历加很多功能 | 加一个小功能并讲透，胜过堆功能 |

## 13. 最后的判断标准

合上电脑，问自己：

1. 我能不能在 1 分钟内让一个没看过项目的人知道它做什么？
2. 我能不能在 5 分钟内画出架构并解释每个箭头？
3. 我能不能讲清 3 个真实问题，而不是 10 个名词？
4. 我能不能诚实说明 AI 参与程度，同时证明我做过工程判断？
5. 我能不能独立改一个小功能并验证？

五个都能，项目就是你的了。
