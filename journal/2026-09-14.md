## New Knowledge

- `wiremock` 的 matcher 不只可以匹配 method 和 path，也可以用 `body_json` 验证请求 JSON body。
- provider 非 2xx status 的测试必须先保证 config 合法，否则测试会提前停在配置校验阶段。
- mock path 必须和真实请求路径一致，否则测试失败原因可能变成 mock 未命中，而不是目标错误路径。
- CLI 集成测试主要保护用户可见契约：stdout、stderr、exit code、真实 binary 调用和配置读取边界。
- 单元测试更适合保护小的内部逻辑，例如请求体构造、status 判断和 response JSON 解析。
- 集成测试通常比单元测试更能抵抗内部重构，因为它关注外部行为而不是函数签名。
- `mod openai;` 的作用是把 `src/openai.rs` 加入 crate 模块树；文件存在不代表模块会自动参与编译。
- `reqwest::Client` 内部可能管理连接池、TLS、timeout 等配置，不适合在高频请求场景里反复创建。

## Problems Encountered

- 初始 provider 401 测试缺少 `api_key`，导致测试提前失败在 `missing llm api key`，没有真正走到 provider 错误路径。
- mock path 曾写成 `/chat/completion`，与真实请求路径 `/chat/completions` 不一致。
- 在当前沙箱环境中运行 `wiremock` 测试需要允许本地端口绑定，否则 mock server 无法启动。
- `tests/chat_cli.rs` 仍有部分 JSON/TOML 字符串缩进和空行格式可以继续清理。

## Key Takeaways

- 测试应该保持单一变量：如果目标是 provider 401，就要让配置校验通过。
- 非 2xx provider 错误路径应该表现为失败 exit code 和 `stderr` 错误信息，而不是正常 `stdout` 输出。
- `body_json` matcher 能验证 CLI 参数和 config 是否真正进入 HTTP request body。
- 当前 `chat` 的测试覆盖已经足够进入下一个小目标，不需要继续堆更多低收益测试。
- 当前阶段不急着重构 `src/openai.rs` 命名或 `reqwest::Client` 复用；这些设计可以等 Agent Runtime 复杂度出现后再处理。

## Engineering Decisions

- 保留 `src/openai.rs` 当前命名，暂不重命名为 `llm/openai_compatible.rs`。
- 保留 `send_chat_request()` 内部创建 `reqwest::Client` 的实现，当前 CLI 一次执行只发一个请求，暂不引入 runtime 级 client 复用。
- 认为 `chat` CLI 集成测试当前应覆盖 happy path、缺少 API key、provider 非 2xx 和请求体匹配；暂不继续补 Authorization header matcher。
- 将未来 client 复用放到 Agent Runtime 阶段讨论，而不是在当前 CLI/HTTP 学习阶段提前抽象。
