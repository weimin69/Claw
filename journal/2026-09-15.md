## New Knowledge

- CLI 用户契约通常由 `stdout`、`stderr` 和 exit code 三部分组成。
- 成功路径应该把可消费结果写入 `stdout`，错误路径不应该污染 `stdout`。
- `stderr` 适合承载错误、诊断和解释信息。
- `wiremock` 的核心价值是让测试确定、快速、可重复，不依赖真实 provider。
- 测试 helper 应该隐藏机械准备步骤，而不是隐藏测试意图。
- 配置合法性和命令运行前置条件不是同一件事。
- 全局非法的配置适合放在 `config.rs` 校验；某个命令运行时才需要的条件适合放在命令层校验。
- Provider 协议细节属于 `openai.rs`，不应该泄漏到 `chat.rs`。
- `Option<String>` 可以显式表达 provider 响应中的字段可能缺失或为 `null`。
- 如果希望区分“JSON 不合法”和“JSON 合法但业务字段缺失”，可以先用 `Option` 建模，再在业务位置给出清晰错误。
- 从借用的数据结构中不能直接移动 `String` 字段；当前使用 `.clone()` 是为了取得 owned `String`。
- 函数返回值来自函数内部构造的数据时，通常需要返回 owned value，而不是返回引用。

## Problems Encountered

- `wiremock` 测试在 sandbox 中不能绑定本地端口，需要在允许本地端口的环境下运行。
- 抽取 `write_temp_config` 后，曾误把不需要 `MockServer` 的 missing API key 测试改成依赖 `server.uri()`，导致 `server` 不在作用域内。
- `chat_rejects_missing_api_key` 一开始误用了不必要的 `format!`，后续已移除。
- `src/openai.rs` 的测试 fixture 只做了轻微整理，后续按用户要求不继续纠结格式细节。
- `PROJECT_STATUS.md` 实际位于 `journal/PROJECT_STATUS.md`，与项目说明中的根目录路径不一致。

## Key Takeaways

- 测试不是越多越好；当前 `chat` CLI 集成测试已经覆盖了关键用户契约，不需要继续堆重复测试。
- 好的测试应该清楚表达行为：运行什么命令、期望成功还是失败、stdout/stderr/exit code 分别是什么。
- Helper 抽取的目标不是减少行数，而是让测试意图更清楚。
- 错误应该由最理解其语义的层产生。
- `config.rs` 负责配置通用合法性，`chat.rs` 负责命令运行前置条件，`openai.rs` 负责 provider 协议和 HTTP 边界，`main.rs` 负责最终展示错误。
- `Option` 在 Rust 中不是绕开错误，而是把“值可能不存在”显式建模。

## Engineering Decisions

- 暂时不扩展 Agent Runtime。
- 暂时不继续增加 `chat` CLI 集成测试。
- 保留 `chat.rs` 中对空 API key 的校验，不把它提升到 `config.rs`。
- 保留 `openai.rs` 中 `content: Option<String>` 的设计，以便区分 provider 响应缺少内容和 JSON 解析失败。
- 当前可以接受 `parse_chat_response` 中的 `.clone()`，不提前做性能或所有权层面的复杂优化。
