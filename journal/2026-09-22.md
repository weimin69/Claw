## New Knowledge

- `.await` 不会自动创建并发；连续 `.await` 通常仍是顺序控制流。
- 多个任务必须先创建，再等待结果，它们的生命周期才能重叠。
- `tokio::spawn` 将 Future 交给 Tokio runtime 调度，并返回 `JoinHandle`。
- `JoinHandle::await` 返回的 `JoinError` 表示任务 panic、取消等任务级失败。
- 启动顺序、完成顺序、获取结果顺序和输出顺序是不同概念。
- `#[tokio::test(start_paused = true)]` 可以使用虚拟时间确定性测试异步时间行为。
- timeout 阈值必须能区分正确实现和目标回归；2.5 秒可以区分 2 秒并发与 3 秒顺序执行。

## Problems Encountered

- 最初在 `tokio::join!` 的返回值后再次使用 `.await?`，混淆了宏已等待 Future 和结果元组的边界。
- Task 最初返回 `()`，没有把等待秒数作为异步块的末尾表达式返回。
- 曾在两个 Task 完成后额外 sleep 两者时长之和，破坏了并发练习目标。
- 输入校验最初遗漏 `0`，并混淆 `&&` 与 `||` 的语义。
- CLI 测试最初写错 binary 名，并留下没有对应函数的 `#[test]` 属性。
- 顺序测试最初使用相同参数，无法发现结果被反向输出的问题。
- 并发单元测试最初误用 `Duration::from_secs(2500)`，使 timeout 无法区分并发和顺序实现。
- 沙箱首次阻止 wiremock 绑定本地端口；允许本地回环端口后完整测试通过。

## Key Takeaways

- 是否形成并发取决于任务创建时机，而不是 `await` 的表面数量。
- 先 `spawn A`、再 `spawn B`、然后依次 await，仍可保持两个任务并发推进。
- CLI 输出顺序应由主流程控制，不能依赖并发任务的完成顺序。
- 只验证最终输出不能证明并发；测试必须加入能区分并发与顺序实现的时间约束。
- 输入应在启动任何 Task 前完整校验，避免命令失败时遗留不必要的已启动任务。

## Engineering Decisions

- 使用固定两个参数的最小命令学习 Task，不提前引入 channel、任务集合或 Agent Runtime 抽象。
- Task 内只执行等待并返回结果，主流程统一输出，保证 CLI 输出确定。
- 使用 Tokio 虚拟时间而不是墙上时间断言，降低测试受机器负载影响的风险。
- CLI 集成测试负责用户可见契约，模块单元测试负责并发时序契约。
