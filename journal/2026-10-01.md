## Today's Goal

完善 Agent 工具错误边界，并开始实现第一个使用结构化输入的内置工具执行器。

## What Was Completed

- 新增失败型 ToolExecutor，验证工具错误会立即终止 Agent Loop。
- 为工具错误补充 Runtime 上下文，错误中包含失败工具名称。
- 使用 `anyhow::Error::chain()` 验证外层上下文与底层原因均被保留。
- Agent 模块测试增加到 10 个。
- 新增 `src/tools.rs` 并注册 `tools` 模块。
- 定义结构化 `AddInput { a, b }`，使用 JSON 作为工具输入。
- 实现 `execute_add()`，覆盖正常输入、缺少字段和整数溢出。
- 实现 `BuiltinToolExecutor`，支持 `add` 分发并对未知名称返回错误。
- 工具模块当前有 4 个测试；完整测试共 58 个并全部通过。

## New Knowledge

- `?` 遇到工具错误时会立即结束 `run_agent()`，不会继续调用模型。
- `with_context()` 由 `anyhow::Context` trait 提供，必须把 trait 引入作用域。
- `error.to_string()` 只显示最外层错误，`error.chain()` 可以检查完整因果链。
- ToolExecutor 应负责识别已注册和未知工具，Agent Runtime 不应硬编码具体工具名。
- unit struct 没有字段，但仍然是完整类型，可以实现 trait。
- `serde_json::from_str()` 需要通过变量类型标注或 turbofish 明确反序列化目标。
- `checked_add()` 使用 `Option` 表达整数溢出，可转换成可控业务错误。

## Problems Encountered

- 初次使用 `with_context()` 时遗漏了 `anyhow::Context` 导入。
- 错误断言中混用了单引号与反引号。
- 结构体字段初始化一度使用 `=` 而不是 `:`。
- 一度把 `anyhow::Error` 类型当作具体错误值，随后改用 `anyhow!()` 创建错误。
- JSON 参数最初没有写成 Rust 字符串，随后使用 raw string 表达。
- 完整测试在受限沙箱中因 wiremock 无法绑定端口而失败；允许本地端口后全部通过。

## Key Takeaways

- Runtime 负责给工具错误增加统一上下文，具体工具负责提供底层失败原因。
- 工具输入不应依赖模糊的位置字符串；结构化 JSON 更接近真实 Tool Calling。
- `add` 的价值是验证完整工具链路，而不是提供复杂计算能力，因此不继续扩展其业务范围。
- 分发器应位于工具执行层，新增工具不应要求修改 Agent Loop。

## Engineering Decisions

- 工具错误默认包含工具名，但不包含完整输入，避免泄露潜在敏感数据。
- 第一版内置工具使用结构化 JSON：`{"a":2,"b":3}`。
- 使用 `i64` 和 `checked_add()`，将溢出转换成明确错误而不是 panic。
- `BuiltinToolExecutor` 当前使用简单 `match` 分发；暂不引入 Tool Registry。
- `add` 保持双操作数最小实现，不扩展为通用计算器。
