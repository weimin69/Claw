## New Knowledge

- 模块名应表达当前稳定职责；Provider 数量增加不等于协议实现数量增加。
- 应在第二种真实实现出现后，再根据实际共同点设计 trait。
- 将具体 `reqwest::Client` 移到函数外可以集中配置和复用连接，但不会自动让网络层可替换或可 mock。
- `.await` 暂停当前 `Future`，让 Tokio runtime 可以执行其他可运行任务，而不是阻塞整个操作系统线程。
- `?` 在遇到 `Err` 时让当前函数提前返回；错误打印和退出码处理仍属于最外层 `main()`。
- `--max-chars` 在完整读取 body 后才截断输出，因此不限制下载量或内存占用。
- wiremock 返回 404 通常表示请求已到达 mock server，但 method、path、header 或 body matcher 未命中。

## Problems Encountered

- 最初将设计决定“改名”误解为允许 AI 直接修改代码，违反了本项目默认由开发者编写生产代码的协作边界。后续必须在任何代码修改前获得明确实施授权。
- 在受限环境中运行 wiremock 测试时无法绑定本地端口；获得权限后重新运行，相关测试全部通过。
- 对 wiremock 404 的初始判断偏向 prompt 或 API key 校验，随后明确配置校验失败发生在请求之前，而 mock 404 表示 matcher 未命中。

## Key Takeaways

- 当前实现支持的是 OpenAI-compatible 协议，而不是只能访问 OpenAI 官方 Provider。
- 准确命名可以减少误解，但目录层级、trait 和依赖注入应由实际变化需求触发。
- 默认错误信息应安全、稳定且由 CLI 控制；verbose 也不意味着原样输出不可信数据。
- 输出长度限制与响应体资源限制是两个不同问题。
- 测试应优先保护高风险错误路径和用户可观察契约，而不是机械追求每个命令相同覆盖量。

## Engineering Decisions

- 使用 `openai_compatible.rs` 表达当前协议边界，暂不创建 `llm/` 目录。
- 当前不引入 Provider trait；出现第二种不兼容协议后再提取真实公共接口。
- 当前继续在单次请求函数中创建 `reqwest::Client`；当一次进程或 Agent run 需要多次 LLM 调用时重新评估。
- 当前非 2xx 错误只显示 HTTP status，未来如增加 `--verbose`，仍需长度限制、脱敏和安全处理。
- 当前 `LlmConfig` 不进一步分层，`parse_chat_response()` 保持模块私有。
- 下一项开发应继续 Async Rust，选择一个能自然练习 Tokio Task 与并发的小功能。
