## New Knowledge

- `response.status()` 用于读取服务器返回的 HTTP 状态码
- `status.is_success()` 用于判断状态码是否属于成功范围
- `reqwest::get(url).await?` 默认不会把 404/500 当作错误，因为请求已经成功拿到了 HTTP response
- `error_for_status()` 适合将 4xx/5xx 转换为错误并通过 `?` 提前返回
- HTTP 请求失败、HTTP 非成功状态码和 body 读取失败是三个不同层次的问题
- `Option<T>` 表示值可能存在或不存在
- `Some(value)` 表示有值，`None` 表示没有值
- `Some(_)` 表示只关心“有值”，不关心具体内容
- `match &config.openai` 可以借用 `Option`，避免移动配置字段
- `Option` 在配置模型中表示字段可以缺失，但具体业务命令仍然可以要求该字段必须存在

## Problems Encountered

- 一开始对 `.await` 的描述不够精确，后来修正为“等待并驱动 Future 完成，然后产生输出”
- 对 `error_for_status()` 的使用边界需要通过业务策略来判断，而不是机械套用
- 新增 `OpenAiConfig.api_key` 后出现 `field api_key is never read` warning，原因是只匹配了 `Some(_)`，没有真正读取字段
- 修改 `read-config` 时遇到 `expected Result<(), Error>, found ()`，原因是函数最后一个表达式不是 `Ok(())`
- 曾误删 `use anyhow::Result`，导致 Rust 将 `Result<()>` 解析为标准库 `Result<T, E>`，出现泛型参数数量错误
- 曾写成 `use anyhow::{Result};`，格式检查提示应简化为 `use anyhow::Result`

## Key Takeaways

- `.await?` 应拆开理解：先 `.await` 得到 `Result`，再由 `?` 处理 `Ok` 或 `Err`
- 简单抓取命令可以选择把非 2xx 状态码作为普通输出，而真实 API 命令通常需要更明确的错误策略
- OpenAI API 调用不只是 HTTP 请求，还包括认证、JSON schema、状态码映射和响应解析
- 模块拆分应按变化原因划分：CLI 命令行为和 OpenAI API 细节属于不同变化原因
- 当前可以先用具体的 `src/openai.rs`，等第二个 provider 或真实复用压力出现后再抽象 trait
- 配置中 `Option<OpenAiConfig>` 表示配置文件允许缺少 OpenAI 配置；未来 `chat` 命令运行时仍然必须检查 API key
- 密钥相关输出只能说明是否设置，不能打印真实值

## Engineering Decisions

- `fetch` 遇到非成功 HTTP status 时打印 `status` 并返回 `Ok(())`，暂时不将 404/500 视为 CLI 失败
- 当前不使用 `error_for_status()`，因为本阶段需要显式理解 HTTP 状态码边界
- 未来 `chat` 命令应对 401、429、5xx 等状态码做更具体的错误映射
- 第一版 OpenAI API 请求细节应放在独立模块中，而不是直接写在命令模块里
- 暂时不引入 `trait LlmClient`，避免在只有一个 provider 时提前引入 async trait、trait object、泛型和错误抽象复杂度
- 第一版 `chat` prompt 倾向使用位置参数，保持 CLI 行为和实现都足够简单
- OpenAI 配置采用结构化 TOML：

```toml
[openai]
api_key = "..."
```

- `Config.openai` 设计为 `Option<OpenAiConfig>`，避免缺少 OpenAI 配置时破坏不依赖 OpenAI 的命令
