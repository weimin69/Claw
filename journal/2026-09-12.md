## New Knowledge

- `clap` 负责命令行参数解析；`serde` 负责 TOML/JSON 等结构化数据的序列化和反序列化。
- `fetch` 当前读取 HTTP body text，不会反序列化为 Rust struct。
- `chat` 的稳定测试应使用 mock server，而不是真实 OpenAI-compatible API。
- `assert_cmd::Command::cargo_bin(...)` 的 binary 名应匹配 `Cargo.toml` 中的 package/bin 名。
- `cargo test --test chat_cli` 使用的是测试 target 名，不带 `.rs` 后缀。
- `tempfile::NamedTempFile` 适合在集成测试中创建临时配置文件。

## Problems Encountered

- 一开始把 `fetch` 的 CLI 解析误认为是 `serde`。
- 一开始把 `fetch` response text 误认为会反序列化成 Rust 结构体。
- `set_body_string` 中普通字符串和 raw string 混用，导致 Rust 字符串解析错误。
- 把 `write!(...)` 写在测试函数外，导致顶层 item 和执行语句混淆。
- 使用了错误的 binary 名 `agent-rust-cli`，导致 `CARGO_BIN_EXE_agent-rust-cli` 未设置。
- `wiremock` 在普通沙箱中无法绑定本地端口，需要在允许本地端口的环境下运行相关测试。

## Key Takeaways

- 测试边界要和代码职责边界一致。
- CLI 参数合法性属于用户输入契约，应通过 CLI 集成测试保护。
- 纯函数算法适合用单元测试保护。
- LLM/HTTP 相关测试应优先确定性、低成本、无密钥依赖。
- 第一个集成测试应先覆盖 happy path，再逐步增加错误路径。

## Engineering Decisions

- `chat` 的第一个 CLI 集成测试选择使用 `wiremock`，不调用真实 provider。
- 临时 config 放在系统临时目录，由 `NamedTempFile` 管理生命周期。
- `base_url` 在测试中写为 `server.uri()`，由 production code 自动拼接 `/chat/completions`。
- 缺少 API key 的测试不需要 mock server，因为错误应在 `chat::execute()` 中提前返回。
