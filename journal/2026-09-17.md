# 2026-09-17

## Today's Goal

为 `chat` 命令补齐 `AGENT_CLI_LLM_API_KEY` 环境变量 fallback 的 CLI 集成测试，并复盘配置来源优先级与 `reqwest::Client` 生命周期边界。

## What Was Completed

- 为 `chat` 添加 CLI 集成测试：配置文件不写 `llm.api_key`，但通过 `cmd.env("AGENT_CLI_LLM_API_KEY", "env-key")` 提供环境变量时，请求仍可成功。
- 在测试中断言 `Authorization: Bearer env-key`，证明 env fallback 结果真实进入 HTTP 请求契约。
- 继续断言成功路径的 stdout 和 stderr 契约。
- 复盘了为什么环境变量应设置在 `assert_cmd` 启动的子进程命令上，而不是使用 `std::env::set_var()` 修改当前测试进程。
- 复盘了当前 `send_chat_request()` 内部创建 `reqwest::Client` 的设计，以及未来 Agent Runtime 中复用 client 的边界。

## New Knowledge

- `cmd.env(...)` 只影响当前被测 CLI 子进程，更适合 CLI 集成测试。
- `std::env::set_var(...)` 修改当前测试进程的全局环境变量，可能污染并发测试。
- 如果配置文件中写了 `api_key`，测试会退化为普通 happy path，无法证明 env fallback 生效。
- stdout 保护用户结果契约，stderr 保护错误/诊断输出契约，Authorization header 保护 provider HTTP 请求契约。
- 当前一次 CLI 调用只发一次 LLM 请求，因此在 `send_chat_request()` 内部创建 `reqwest::Client` 可以接受。
- 未来 Agent Loop 多次调用 LLM 时，应考虑把 HTTP client 提升为更长生命周期的 `LlmClient` 或 runtime-owned client。

## Problems Encountered

- 最初测试中出现过 async test attribute、变量拼写、缺少分号、header 值、配置文件误写 `api_key`、错误使用 `config_path` 等问题。
- 在沙箱环境中运行 `wiremock` 测试时遇到本地端口绑定权限限制，但开发者本地运行后测试通过。
- 对 `chat.rs` 是否应负责创建 HTTP client 的职责边界有过误判，随后通过模块职责复盘澄清。

## Key Takeaways

- 集成测试不只验证“能成功”，还应验证关键边界是否真的生效。
- 测 env fallback 时，配置文件必须故意省略对应字段。
- 测试中的外部状态要尽量缩小作用域。
- 抽象应由重复、边界或变化压力推动，而不是由“未来可能需要”推动。
- 当前阶段优先保持简单清晰；Agent Runtime 阶段再引入更长生命周期的 client。

## Engineering Decisions

- 保持 `config.rs` 负责配置来源、默认值、env fallback 和配置校验。
- 保持 `openai.rs` 负责 OpenAI-compatible 请求构造、HTTP 调用、status 判断和响应解析。
- 暂不把 `reqwest::Client` 从 `send_chat_request()` 提前移动到 `chat.rs`。
- 将未来 client 复用问题保留到 Agent Runtime 或多次 LLM 请求需求出现时处理。
