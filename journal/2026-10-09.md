## New Knowledge

- 工具定义负责向模型声明能力，`execute_add()` 负责真正执行能力。
- JSON Schema 描述工具参数的结构和约束，不执行工具逻辑。
- 协议 DTO 表达外部 API JSON 的形状，领域模型表达 Agent Runtime 内部语义。
- 无状态模型请求需要在每轮重新发送必要的 `User → ToolCall → ToolResult` 历史。
- `#[serde(skip_serializing_if = "Vec::is_empty")]` 可以避免空字段改变既有协议请求。
- `#[serde(default)]` 可以让响应缺少 `tool_calls` 时得到空 `Vec`。
- 函数遇到 `return` 会立即结束，因此当前解析逻辑优先返回 `ToolCall`。
- `reqwest::Client` 放入模型适配器后可以在多轮 Agent 调用中复用。

## Problems Encountered

- 给 `ChatRequest` 增加空 `tools` 后，Wiremock 请求体 matcher 未命中并返回 404。
- 混淆了函数参数类型 `&[AgentMessage]` 与结构体字段所需的实际值。
- 新增请求构造器时出现重名函数、错误参数和 `Vec!` / `vec!` 混淆。
- 复制位置示例时误把 `// ...` 占位函数和重复 DTO 一并复制，导致语法错误。
- 测试数量和重复 JSON fixture 开始影响理解，因此删除了重复的 DTO 细节测试，保留面向 `ModelDecision` 的行为测试。
- 对 `ToolCall` 与 `FinalAnswer` 分支优先级、完整历史和 DTO 边界仍需要系统复习。

## Key Takeaways

- 模型看不到 Rust 内部工具实现，必须通过结构化工具定义显式告知。
- Agent 请求不仅需要当前结果，还需要完整的因果上下文。
- 暂不支持的协议能力应明确报错，不能静默忽略。
- 测试应保护有意义的行为边界，避免重复测试私有实现细节。
- 当前代码继续扩展前，应先建立对已有文件、类型、控制流和测试目的的整体理解。

## Engineering Decisions

- 保留普通 `build_chat_request()`，新增 Agent 专用请求构造器，避免一次性破坏已有 CLI。
- 空 `tools` 不序列化，维持普通 chat 的既有请求契约。
- 当前保持单工具顺序 Runtime；模型返回多个工具调用时明确失败。
- `OpenAiCompatibleAgentModel` 持有并复用 `reqwest::Client`。
- 暂停所有新功能，明后天只进行整个项目的逐文件、逐行复习。
