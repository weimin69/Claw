## New Knowledge

- `async fn` 调用后返回的是 `Future`，需要 `.await` 驱动到完成
- `.await` 负责等待 `Future` 完成并取出输出，`?` 负责处理输出里的 `Result`
- `#[tokio::main]` 会生成 runtime 启动代码，并在 runtime 中执行 async `main`
- async 不是为了“变成多线程”，而是为了等待外部资源时不长期占住当前线程
- HTTP 请求通常至少包含两个异步等待点：等待响应、读取响应 body
- Rust 字符串应按 `chars()` 截取字符预览，避免按字节切片破坏 UTF-8 边界

## Problems Encountered

- 对 `.await` 的理解一开始偏向“检查 Future 是否执行”，后来修正为“等待并驱动 Future 完成”
- 对 `reqwest::get(url).await?` 和 `response.text().await?` 的等待对象一开始区分不够清楚
- Codex 执行环境中访问 `https://example.com` 出现 DNS 失败，但本机运行成功，判断为环境网络限制而非代码问题

## Key Takeaways

- async 调用链的顺序应理解为：先 `.await` 拿到结果，再用 `?` 处理错误
- 同步命令和异步命令可以在同一个 CLI 中共存，不需要为了统一而全部 async
- 新增命令仍遵循固定结构：CLI enum、命令模块、模块导出、`main.rs` 分发
- HTTP 状态码和网络错误不是同一类问题，后续需要单独学习 `status()` 或 `error_for_status()`

## Engineering Decisions

- `fetch::execute(url: &str)` 设计为 `async fn`，因为真实 HTTP 请求需要等待外部网络资源
- `fetch` 暂时只打印前 200 个字符，保持学习目标聚焦在 HTTP 请求模型，而不是 HTML 处理
- 暂时使用 `reqwest::get` 的最小接口，而不是立即引入可复用 client、超时、headers 或复杂错误模型
- 不把已有同步命令改成 async，避免制造不必要的接口复杂度
