## New Knowledge

- `Serialize` 用于 Rust 数据结构到外部格式，`Deserialize` 用于外部格式到 Rust 数据结构。
- `.json(&request)` 依赖 `reqwest` 的 `json` feature，并会使用 `serde` 序列化请求体。
- OpenAI-compatible Chat Completions 请求使用 `messages` 数组，而不是 Responses API 的 `input` 字段。
- `bail!()` 适合主动判断业务状态失败并返回新错误。
- `.context()` 适合给已有失败的 `Result` 增加上层语义。
- HTTP `401 Unauthorized` 是服务器返回的失败响应，不是 `.send().await?` 层面的网络错误。
- `choices.first()` 比 `choices[0]` 更安全，因为空数组不会 panic。

## Problems Encountered

- `reqwest::RequestBuilder` 找不到 `.json()`，原因是 `reqwest` 没启用 `json` feature。
- `ChatRequest` 构造时加入了 `stream` 字段，但 struct 定义一开始没有同步增加该字段。
- 测试断言里的多行字符串导致错误信息匹配失败。
- 早期非 2xx status 和空响应内容返回 `Ok(String::new())`，会让失败请求看起来像成功。
- provider 错误 body 中可能包含脱敏后的 key 片段，直接输出不够安全。

## Key Takeaways

- 能跑通 API 不是结束，失败路径是否清晰同样属于功能质量。
- API 调用可以分成请求构造、HTTP 发送、status 判断、body 读取、响应解析几个边界。
- 真实 API 调用适合验证端到端链路，响应解析和 status 判断应优先用确定性单元测试覆盖。
- 支持多个 OpenAI-compatible provider 时，不应该在本项目中写死模型白名单。
- 密钥相关信息即使被 provider 脱敏，也不应该随意出现在默认 CLI 错误输出中。

## Engineering Decisions

- 配置统一收敛到 `[llm]`，因为 `base_url`、`api_key`、`model`、`temperature` 都属于 LLM provider 配置。
- 默认 `base_url` 使用 `https://api.openai.com/v1`，DeepSeek 等 provider 通过配置覆盖。
- 保留 Chat Completions 请求结构，以支持 DeepSeek 等 OpenAI-compatible provider。
- `api_key` 缺失仍作为 `chat` 命令运行条件处理，而不是全局配置合法性处理。
- 非成功 HTTP status 只暴露 status，不默认打印 provider 原始 body。
- 响应解析逻辑从 HTTP 发送函数中抽出，便于单元测试。
