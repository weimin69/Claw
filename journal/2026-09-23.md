## New Knowledge

- `JoinHandle<T>::await` 返回 `Result<T, JoinError>`。
- 当 Task 自身返回 `Result<T, E>` 时，等待结果是 `Result<Result<T, E>, JoinError>`。
- `bail!` 正常返回业务 `Err`，不会产生 `JoinError`。
- Task panic 或被取消时，Task 无法正常返回，等待者会得到 `JoinError`。
- `handle.await??` 可以连续传播外层和内层错误，也可以拆成多步以明确错误边界。
- 丢弃 `JoinHandle` 默认不会自动取消 Task，Task 可能继续在 runtime 中运行。
- wait-all 要先保存所有 handle 的完整等待结果，再统一传播错误。
- 使用暂停时间和 `Instant::elapsed()` 可以确定性证明失败后仍等待了另一个 Task。

## Problems Encountered

- 最初把 Future 返回业务错误误认为外层 `JoinError`。
- 一度认为恢复成 `handle.await?` 会无法编译，忽略了第一个 `?` 只拆外层结果。
- 使用 `match` 消费了 `Result` 的所有权，之后又尝试再次使用已移动的值。
- 在 `match` 分支内创建的局部变量无法在分支外输出。
- 意外导入不存在且无关的 `serde_json::ser::First`。
- wait-all 测试最初遗漏 `.await`，因此拿到 Future 而不是执行结果。
- 测试最初使用了未导入的 `Instant`，并把测试专用导入放到生产模块导致警告。
- 新增测试后需要运行 `cargo fmt` 才能通过格式检查。

## Key Takeaways

- 外层错误回答“Task 是否正常结束”，内层错误回答“业务是否成功”。
- 业务失败与 Task 运行失败必须分别建模、测试和传播。
- fail-fast 和 wait-all 是不同的工程策略，不能由 `?` 的摆放位置偶然决定。
- wait-all 会增加失败返回延迟，但避免因提前返回而留下未等待的兄弟 Task。
- 测试必须覆盖实际生产编排函数；只测试孤立 Task 的错误类型不能保护 wait-all 策略。
- 错误传播时机是并发控制流的一部分，而不仅是语法细节。

## Engineering Decisions

- 当前 `parallel-wait` 采用 wait-all，而不是 fail-fast。
- 先等待两个 handle，再按固定顺序处理 `JoinError` 与业务错误。
- 抽取私有 `wait_for_both()`，使并发编排策略能够被单元测试直接覆盖。
- 不为测试向 CLI 增加 `--panic-first` 等人工参数，避免测试需求污染用户接口。
- 暂不引入显式取消、channel 或更通用的泛型并发抽象。
