## New Knowledge

- `value_parser = parse_positive_usize` passes a parser function to clap; it does not call the function immediately.
- Function items can be handed to another API and called later by that API.
- A Rust function can return its final expression without `return`, as long as the final expression has no semicolon.
- `String::len()` counts bytes, while `.chars()` iterates Unicode scalar values.
- Some clap parser helpers support `.range()`, but `value_parser!(usize).range(...)` was not available in the current dependency setup.
- `#[cfg(test)] mod tests` must live at module level, not inside another function body.

## Problems Encountered

- `value_parser!(usize).range(1..)` failed because the inferred parser did not expose `.range()`.
- The first unit test attempt placed `assert_eq!` at item level instead of inside a test function.
- The test module was briefly placed inside `preview_text`, causing a syntax error.
- `wiremock` integration tests failed inside the sandbox because the test process could not bind a local port; the same tests passed outside the sandbox.

## Key Takeaways

- CLI parameter validation belongs close to clap when the problem is invalid user input.
- HTTP status errors belong in the command execution layer because they are request result errors.
- Unit tests are best for pure deterministic logic.
- CLI integration tests are best for user contracts: arguments, stdout, stderr, and exit code.
- A new CLI option is not fully covered until both the pure logic and the full command path are tested.

## Engineering Decisions

- `--max-chars` defaults to `200` to preserve the old fetch preview behavior.
- `max_chars` remains a `usize` in command execution because it feeds directly into iterator `.take(max_chars)`.
- `parse_positive_usize` rejects `0` at clap parsing time to avoid treating invalid CLI input as an HTTP execution concern.
- `preview_text` uses `.chars()` instead of byte slicing to avoid breaking UTF-8 text.
