## Today's Goal

完成 `chat` 命令空白 prompt 的错误路径集成测试，并理解同步 stdin 在当前一次性 CLI 与未来异步 Agent Runtime 中的边界。

## What Was Completed

- 复盘了 `Option<String>` 如何表达命令行 prompt 是否存在。
- 区分了输入来源选择与最终 prompt 业务校验。
- 明确命令行 prompt 优先于 stdin；显式空白参数不会静默回退到 stdin。
- 添加 `chat_rejects_whitespace_argument_prompt` CLI 集成测试。
- 添加 `chat_rejects_whitespace_stdin_prompt` CLI 集成测试。
- 验证失败 exit code、空 stdout 和稳定 stderr 错误信息。
- `git diff --check`、`cargo fmt --check` 和 `cargo check` 通过。
- 两个新增 `chat` CLI 集成测试通过。

## New Knowledge

- `Option<String>` 只表达参数是否存在，不负责判断字符串内容是否合法。
- 应先根据优先级选择输入来源，再对最终 prompt 统一执行 `trim().is_empty()` 校验。
- 异步 I/O 的主要价值不是让单次 I/O 更快，而是在等待 I/O 时允许运行时执行其他任务。
- 当前 `chat` 是一次性顺序流程，等待 stdin 时没有其他任务需要推进，因此同步读取暂时可以接受。

## Problems Encountered

- 第一个测试最初将错误信息写成 `can not`，而生产契约是 `cannot`，导致断言失败。
- 第一个测试名称最初使用 `missing`，没有准确表达“参数存在但只包含空白”的场景。
- 第二个测试最初缺少普通空格输入，且存在一个多余空行，导致 `cargo fmt --check` 失败。
- 在受限环境中运行全部 `chat_cli` 测试时，Wiremock 无法绑定端口；因此本次使用测试名称过滤器单独验证两个不需要 MockServer 的新增测试。

## Key Takeaways

- 输入来源是否存在与输入内容是否合法是两个不同问题。
- 显式输入的优先级规则应该确定且可预测，不能在内容非法时静默换用其他来源。
- 错误路径集成测试应保护 exit code、stdout 和 stderr 等用户可观察契约。
- 是否采用异步 I/O 应由并发、取消和响应性需求决定，而不是因为函数本身是 `async fn`。

## Engineering Decisions

- 保持“命令行 prompt 优先，否则读取 stdin”的现有规则。
- 在来源选择完成后统一拒绝空白 prompt。
- 当前继续使用 `std::io::stdin().read_to_string()`，等交互式 Agent Runtime、流式输出、取消或并发任务出现后再评估异步 stdin。
- 空白 prompt 测试不启动 MockServer，因为正确实现应在网络请求之前失败。
