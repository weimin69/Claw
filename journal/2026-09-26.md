## New Knowledge

- `bail!` 表示 Task 正常结束并返回内层业务错误，不是 Task 运行失败。
- `.context()` 可以添加任务身份和错误层级，同时保留底层错误链。
- wait-all 不等于聚合错误；等待全部完成后仍需明确错误选择与优先级。
- 当前处理顺序先检查两个外层结果，再检查两个内层结果，因此 JoinError 可能优先于更早 Task 的业务错误。
- 测试名称、构造输入和预期结果必须描述同一个失败场景。
- 学习型 CLI 命令不必原样进入最终产品；重要的是把并发、错误和测试能力迁移到 Agent Runtime。

## Problems Encountered

- 对双层 `Result`、wait-all 和错误传播时机出现遗忘，需要重新通过具体类型复习。
- 最初的 CLI 错误断言只匹配通用子串，无法保护 first/second 的精确诊断。
- 新增 second Task 测试后需要运行 rustfmt 才能通过格式检查。
- 双重失败测试第一次错误地构造为 first 成功、second 业务失败，与测试名称和预期不一致。
- 讨论后发现继续深挖学习型命令的错误聚合收益有限，需要及时切换到 Agent 主线。

## Key Takeaways

- 错误上下文应该同时回答“哪个任务”和“哪一层失败”。
- 并发系统中多个错误都真实存在，但 API 通常只能返回一个主错误，因此优先级必须显式设计。
- 测试应精确保护用户诊断契约，而不是只断言发生了某种错误。
- demo 命令的目标是承载一个清晰概念，不应为了复用而演变成提前设计的通用框架。
- CLI、timeout、取消和可观测性可以在 Agent Runtime 出现真实需求时继续学习和补齐。

## Engineering Decisions

- `parallel-wait` 保持 wait-all，不实现多错误聚合。
- 当前错误优先级保持：first JoinError、second JoinError、first 业务错误、second 业务错误。
- first/second 参数和四种 Task 错误来源使用不同上下文。
- 不再继续扩展 `parallel-wait`，未来可在产品清理阶段决定删除或隔离学习型命令。
- 后续路线直接进入 Stage 6 的最小 Agent Runtime；Stage 3/4 的 timeout、取消、日志和 CLI 打磨在 Agent 场景中按需学习。
