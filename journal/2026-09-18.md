## New Knowledge

- stdin 是进程的标准输入通道，prompt 是发送给模型的业务内容，两者不是同一概念。
- `Option<String>` 可以表达命令行参数“提供或缺失”两种合法状态。
- `std::io::Read` trait 提供 `read_to_string()` 方法。
- `read_to_string()` 返回读取的字节数，实际文本写入传入的 `String` 缓冲区。
- `match` 的所有分支必须产生兼容类型；对 `Result<String>` 使用 `?` 可得到 `String` 并传播错误。
- owned `String` 可以直接移动到请求结构中，不需要额外调用 `to_string()`。

## Problems Encountered

- 误导入了 `std::net::Shutdown::Read`，与 `std::io::Read` 发生名称冲突。
- 一度尝试让嵌套函数捕获外层 `prompt`，但普通函数项不能捕获动态环境。
- 混淆了 stdin 读取来源、`String` 缓冲区和 `read_to_string()` 返回值。
- stdin 测试最初只验证 provider 401，没有验证 stdin 内容进入请求体。
- prompt 优先级测试的 matcher 一度期望了 stdin 内容，并出现 `argument` 拼写不一致，导致 wiremock 返回默认 404。

## Key Takeaways

- 输入来源和业务数据应分开建模。
- 先选择最终输入，再统一执行空值等业务校验，能避免不同来源产生不一致行为。
- wiremock 的意外 404 通常意味着 method、path、header 或 body matcher 没有命中。
- 集成测试应验证真正的用户契约和请求契约，不能只证明“发出过请求”。

## Engineering Decisions

- `chat <config_path> [prompt]` 中 prompt 为可选位置参数。
- 同时存在命令行 prompt 和 stdin 时，显式命令行参数优先，stdin 被忽略。
- stdin 读取暂时使用同步标准库 I/O；当前单次 CLI 请求场景保持实现简单。
- 空白 prompt 在输入来源合并后统一拒绝，错误为 `prompt cannot be empty`。
- stdin 行为继续通过 mock server 做确定性集成测试，不调用真实 LLM provider。
